# MVP

> [!NOTE]
> **Status: proposed.** This note describes the first usable version of stream
> and is awaiting review. Names in *italics* are proposed terms still open for
> review. How the system is built (the core, plugins, processes, Jobs, Accounts,
> and the Mode) is in [Architecture](Architecture.md).

## Goal

- Play your music from any device on the home network, in its own browser,
  from **local Libraries** and from **Bilibili**.
- One household: each person signs in to their own Account; the server isn't
  exposed to the internet.
- Unintrusive: stream never moves, renames, or retags your files. What it knows
  about your music lives in its own data folder.

## Decisions at a glance

| Area | Decision | Why |
| --- | --- | --- |
| Architecture | A closely reviewed core; features as plugins in a separate host process, behind toggles | Fast-moving plugin code can't take the server down; see [Architecture](Architecture.md) |
| Playback | Each device plays in its own browser; the server stores and serves audio | Simplest; a phone keeps its own queue |
| Server | Python 3.14, FastAPI, SQLAlchemy 2 + Alembic on SQLite (WAL) | Native HTTP Range for Safari seeking; autogenerated migrations |
| Client | React + Vite + TypeScript | The most mature ecosystem |
| Layout | The song table and queue for browsing; a stage view for Now playing | Fits 16:9 Bilibili covers, messy titles, and keyboard use |
| Accounts | Local Accounts, admin or member; each has its own ratings, playlists, policy, and linked accounts | A household shares the music, not the taste |
| Mode | *Online*, *Offline*, or *Auto* from the server's network; Offline holds Downloads in the *Downloads* tab | No surprise downloads on a hotspot or with no internet |
| Bilibili | yt-dlp as a library, in the `bilibili` plugin; each Account's own login | The only maintained, permissively licensed option; no headless browser |
| Bilibili playback | Adding a Bilibili Track downloads it; a Track without a Download plays once a new Job finishes | A request never waits on a Job |
| Libraries | fsspec in the `fsspec-library` plugin; folders and zip archives now | Network drives later by configuration |
| Tags | tinytag (MIT); a small reader of our own for protected `.m4p` files | mutagen is GPL; tinytag reports no DRM |
| Audio quality | Best available audio by default; a lower tier on request | Your choice; a song is a few MB |
| Download policy | *Smart playlists* marked *Keep downloaded*, one shared *storage limit*, and a *removal order*, all in the core | Rules you write; removal deletes files, so it is reviewed code |
| Over the limit | Rules win: kept songs are never removed to make room; stream warns | A song you asked to keep stays |
| Idempotency | Natural keys, client-chosen ids, absolute values, retry-safe Jobs | A retried request or a restart never duplicates work |
| Data folder | One folder for the database, Downloads, and cache: `STREAM_DATA_DIR`, defaulting to the platform's app-data folder; logins live in the Keychain | One thing to back up; your Libraries stay untouched |
| Toolchain | mypy strict, pytest, Hypothesis, ruff, import-linter; ESLint, Vitest, Playwright | Fully typed; see the instructions files |

## Language

| Term | Meaning |
| --- | --- |
| **Account** | A person in the household, signed in with a username and password; an **admin** or a **member**. |
| *Linked account* | An Account's login on a site, such as Bilibili cookies. |
| **Track** | A piece of music: title, artists, album, duration, artwork. Each Account has its own **favorite**, **rating** (1–5 stars), and play history for it. |
| **Source** | Where a Track's audio comes from: a file in a Library, or a Bilibili video part. A Source can be **missing** (gone at the last scan) or **unavailable** (removed from Bilibili, or its plugin is off). |
| **Library** | A storage root you register: a folder or a zip archive now, a network drive later. stream only reads it. |
| *Download* | The one copy of a Bilibili Source on the server's disk, at an **audio quality**. |
| **Playlist** | An Account's ordered list of Tracks. A *smart playlist* is defined by **rules** instead of a list. |
| *Keep downloaded* | A switch on a smart playlist: every Track it matches should have a Download. Those Tracks are *wanted by* that Account. |
| *Storage limit* | The most disk space Downloads and the cache may use, shared by the household. |
| *Removal order* | Which Download goes first when the limit is reached. |
| *Mode* | *Online*, *Offline*, or *Auto*: whether the server may contact music sites now. |
| **Queue** | What plays next on one device. It lives in that device's browser. |
| **Job** | Background work with progress and a result, such as a Download or a Library scan. The *Downloads* tab lists Download Jobs. |

## Data model

- `account`: username, display name, password hash, role, created.
- `session`: account, token hash, created, last seen.
- `track`: title, artist, album, album artist, duration, added.
- `track_state`: account, track, favorite, rating, play count, last played.
- `source`: track, kind, a unique canonical locator per kind (a path in a
  Library, or a BV id and part), a quick fingerprint (size plus a hash of the
  first and last 64 KB), state (`ok`, `missing`, `unavailable`, `can't play`),
  and kind-specific details as JSON validated by the kind's model.
- `library`: name, fsspec URL and options, the last completed scan.
- `download`: source (unique), file path, audio quality, size, created, last
  served.
- `playlist` and `playlist_entry`: owned by an Account; a smart playlist stores
  its rules and the *Keep downloaded* switch.
- `wanted_by`: account, track; derived from *Keep downloaded* playlists.
- `job`: kind, target, requested by, state, lease, process id, attempts,
  progress, error.
- `plugin_state`: plugin, stored state, faulted.
- Settings: storage limit, removal order, Mode, metered Wi-Fi networks, default
  audio quality.
- Linked accounts live in the macOS Keychain, not in the database.
- **Smart-playlist rules are a typed, versioned schema** (Pydantic), stored as
  JSON with a version number. Rules match on favorite, rating, play count, last
  played, added, artist, album, and Source kind.

## Flows

### Add from Bilibili

- Paste a link. stream accepts only `bilibili.com` and `b23.tv` addresses. The
  plugin resolves short links, canonicalizes `av` and `BV` ids and part numbers,
  and reads the title, uploader, parts, and available qualities. The host is
  checked again after resolving, and yt-dlp only ever sees the canonical URL.
- You edit the cleaned title and artist and pick the quality. Each part you
  choose becomes a Track, and a Download Job starts for it with your linked
  account. Progress streams to every open browser.
- A link that is already in the catalog returns its existing Track.
- **Offline:** the link is saved raw, then canonicalized and added once Online.
- A long mix or live recording stays one Track; splitting by chapter is not in
  the MVP.

### Scan a Library

- A scan is a Job. It first checks that the root is reachable. A previously
  populated Library that now lists no files is marked **offline**, and nothing
  is marked missing.
- Walk the Library, skip files whose size and modification time are unchanged,
  read tags, and mark protected `.m4p` files as *can't play*. Nothing is written
  to the Library.
- **Identity across rescans:** a file at a known path keeps its Source. A new
  path whose fingerprint matches a missing Source is a move; the Source follows
  it, and every Account keeps its ratings, history, and playlists.
- Only a completed scan marks unseen Sources **missing**. A missing Source
  returns when its file reappears. Nothing is deleted.
- The MVP doesn't merge duplicate Tracks, such as the same song in a folder and
  on Bilibili.

### Play

- The browser asks for a Source's audio by its id; the server never takes a
  path from the client.
- The core serves every file itself, with Range: a Library file at its path, a
  stored (uncompressed) zip member at its offset, or a Download. A compressed
  zip member is copied into the cache once, and that copy is served.
- A Bilibili Track without a Download (removed by the policy) answers
  *preparing* with a Job id. The client shows the Track as preparing and plays
  it when the Job finishes; Offline, it shows *available when online*. No
  request waits on a Job.
- Playing records the play in that Account's history.

### Enforce the policy

- **A pure function, `plan(state) -> actions`**, in the core, decides what to
  download and what to remove. The state includes running, waiting, and failed
  Jobs. Running `plan` on its own result changes nothing.
- **One evaluation at a time.** A Download finishing, or a change to a favorite,
  rating, playlist, rule, or the limit, requests an evaluation. Requests that
  arrive while one runs merge into the next.
- **Steps:**
  1. The wanted set is every Track *wanted by* any Account.
  2. Download wanted Tracks that are missing a Download, while the limit allows.
     A running Job reserves its estimated size. Offline, these Jobs wait.
  3. Over the limit, remove cache copies, then Downloads outside the wanted set,
     in removal order, until usage is back under the limit.
  4. If the wanted set alone exceeds the limit, start no more Downloads and show
     a warning in Settings until it is resolved.
- **Never removed:** a wanted Download, a Download served in the last hour (it
  may be playing on some device), and a Download with a running Job.
- **Least favorite order:** Tracks that are no Account's favorite before
  favorites; then by the best rating any Account gave, unrated first; then least
  recently played by anyone (never played first); then oldest added.
- **What the limit counts:** Downloads, cache copies, and running Jobs'
  reservations. The database is not counted. Settings shows the space each
  Account's rules hold.

## Errors and boundary cases

- **Bilibili fails:** the failure is classed as network, auth, or plugin (see
  [Architecture](Architecture.md#failures)). A network failure waits for
  Online; an expired login marks the linked account *needs sign-in*; *Retry*
  reruns a failed Job. Settings shows site health and the yt-dlp version.
- **A video is removed or region-locked after it was added:** its Source is
  *unavailable*; an existing Download still plays.
- **A quality needs a premium login you don't have:** fall back to the best
  available and record the quality actually downloaded. Choosing another quality
  later replaces the Download.
- **Protected `.m4p`:** listed as *can't play* and never served.
- **A Library goes offline** (a drive is unplugged): it is marked offline and its
  Tracks are greyed out, not deleted.
- **A plugin is off, faulted, or quarantined:** its Tracks stay; their existing
  Downloads play, and the policy treats them as unsatisfiable.
- **Interrupted work and duplicate requests:** see
  [Architecture](Architecture.md#jobs).
- **Disk full during a Download:** the Job fails and its temporary file is
  removed.
- **SQLite:** each connection sets a busy timeout, foreign keys, and WAL;
  transactions stay short; only the server process writes.

## Security

- **Sign-in on every request** except the sign-in page; see
  [Architecture](Architecture.md#accounts).
- **Host and Origin checks** reject requests whose `Host` or `Origin` isn't the
  server's own, which blocks cross-site requests and DNS rebinding.
- **Libraries:** only local folders and zip archives in the MVP (an fsspec
  protocol allowlist), registered by an admin. Locators are checked to stay
  inside their Library; `..` and absolute member paths are rejected.
- **Bilibili only:** the link allowlist above; yt-dlp never receives an
  arbitrary URL.
- **Linked accounts** live in the Keychain, reach a Job only as a temporary
  owner-only copy, and are never served or logged.
- **Plain HTTP on the LAN** in the MVP; listens on all interfaces by default,
  since LAN devices must reach it, and the address is configurable.

## Testing

- **Domain:** unit tests plus Hypothesis properties, for example: after
  enforcement, usage fits the limit unless the wanted set alone exceeds it; a
  wanted Download is never removed; `plan` on its own result is a no-op; rules
  round-trip through JSON.
- **Plugins:** each extension point's contract tests, plus the plugin's own
  tests: fsspec's in-memory filesystem and zip fixtures (stored and compressed
  members) for Libraries; a recorded info JSON from a real video for Bilibili.
  Tests never contact Bilibili; a live check is an opt-in marker you run by hand.
- **Plugin host and Jobs:** a plugin that raises, hangs, returns malformed data,
  or crashes, against the host and the Job runner.
- **Web API:** httpx tests for sign-in and for Range: `bytes=0-1`, open-ended,
  suffix (`bytes=-N`), unsatisfiable (416), multiple ranges (answered with the
  first), `HEAD`, `ETag` with `If-Range`, and `audio/mp4` for `.m4a`.
- **Client:** Vitest for components and Playwright for sign-in, playback,
  seeking, and the queue.
- **iOS by hand:** a short checklist per release for the lock screen,
  background playback, and moving to the next Track while locked, which
  Playwright's WebKit can't reproduce.
- **Coverage floors:** 90% line and 85% branch for the core and plugin API; a
  lower floor for plugins.

## Client notes

- **One persistent `<audio>` element**; the next Track swaps its `src`, so
  autoplay keeps working on iOS after the first tap.
- **Queue advance follows the `ended` event**, never a timer.
- **Media Session:** metadata, actions, `playbackState`, and
  `setPositionState`.
- **The queue is saved in IndexedDB**, best effort; the browser may clear it.
- **Views of a disabled plugin are hidden**; the server lists enabled features.

## MVP checklist

- [ ] Sign in and out; an admin creates Accounts; *Sign out everywhere*.
- [ ] Link a Bilibili login to your Account from a cookies file, with its status
      shown.
- [ ] Add a folder or zip Library, scan it, and flag protected files.
- [ ] Add from Bilibili by link: parts, quality, editable title and artist.
- [ ] Play, pause, seek, next, and previous; a per-device queue; lock-screen
      controls through the Media Session API.
- [ ] Favorite and rating; playlists; smart playlists with *Keep downloaded*.
- [ ] Storage limit with *least favorite* removal; a warning when kept songs
      exceed it.
- [ ] Mode: Auto, Online, and Offline; the *Downloads* tab with waiting,
      running, and failed Downloads, and *Retry*.
- [ ] Job progress in every open browser.
- [ ] Settings: Accounts, Libraries, linked accounts, storage, Mode, plugins and
      their health, and the yt-dlp version.
- [ ] `stream backup <file>`: a consistent copy of the database through SQLite's
      backup API; `stream reset-password`; `stream serve --safe-mode`.

**Not in the MVP:** video and MVs, searching Bilibili, importing Bilibili
favorites, network drives, other removal orders, merging duplicate Tracks,
splitting a video by chapter, playback on the server itself, a terminal client,
other music sites, lyrics, HTTPS, third-party plugins, and per-Account storage
quotas.

## Build order

Each step is one branch, designed briefly, built test-first, and merged before
the next. From step 4 on, each step is usable in a browser.

0. **Bilibili check:** confirm that the pinned yt-dlp downloads the sample
   video's audio with your cookies, and record its info JSON as a fixture. If
   it still fails, the Bilibili steps wait for an upstream fix while the rest
   proceeds.
1. **Catalog and Accounts:** Tracks, Sources, Playlists, Accounts, and sessions in
   SQLite, with migrations and sign-in.
2. **Plugin host and Jobs:** the plugin API, the host process, Job processes,
   the Job table and recovery, toggles, and the contract test kit.
3. **Libraries:** the `fsspec-library` and `tinytag-tags` plugins, and scanning.
4. **Playback:** serving audio with Range, and a bare page with sign-in, the
   player, the queue, and lock-screen controls.
5. **Bilibili:** the `bilibili` plugin, linked accounts, and progress events.
6. **Download policy and Mode:** smart-playlist rules, the storage limit,
   removal, and Online and Offline.
7. **Client views:** the song table, queue, stage, add dialog, *Downloads* tab,
   and settings.
